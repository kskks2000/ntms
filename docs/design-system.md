# NTMS 디자인 시스템

관제 화면을 하루 여덟 시간 들여다보는 사람을 위해 만든다. 화려함보다
**정확함**이 먼저다. 숫자는 자릿수가 맞아야 하고, 상태는 색 없이도 읽혀야 하고,
같은 동작은 어느 화면에서나 같은 이름이어야 한다.

- 토큰 정의 : `apps/web/src/app/globals.css`
- 유틸리티 매핑 : `apps/web/tailwind.config.ts`
- 기본 부품 : `apps/web/src/components/ui/`

---

## 1. 방향 — 관제 (Control Room)

이 제품의 주장은 DB 설계 원칙에서 그대로 가져왔다.

> 계획과 실행의 차이를 남긴다.

편성 → 배정 → 배차 → 실행 → 실적 → 정산을 각각 다른 테이블에 두는 이유가
그것이고, 화면이 보여줘야 하는 것도 그 차이다. 그래서 인증 화면의 얼굴은
**운행 다이어그램(Marey 도표)** 이다 — 세로축은 거점, 가로축은 시간, 한 선이
차량 한 대의 하루. 기울어진 구간은 이동, 평평한 구간은 정차.

19세기 파리–리옹 열차 시각표에서 온 형식인데, 지금도 이 산업에서 계획과
실행을 겹쳐 보는 가장 정확한 그림이다. 로그인 화면이 제품의 관점을 미리
보여주고, 로그인 이후 배차판이 같은 형식을 이어받는다.

**한 곳에만 힘을 준다.** 다이어그램이 유일한 볼거리이고, 나머지는 전부
헤어라인과 여백으로 조용히 둔다.

## 2. 토큰 3계층

```
원시(primitive)  --c-ink-850     색 자체의 이름. 팔레트를 갈아끼우는 지점
       ↓
의미(semantic)   --surface-card  역할의 이름. 라이트/다크가 갈리는 유일한 층
       ↓
컴포넌트         --control-h-md  특정 부품의 치수
```

**컴포넌트는 의미 토큰만 본다.** 화면 코드에서 `bg-canvas-850` 같은 원시
토큰을 직접 쓰기 시작하면 그 자리에서 다크모드가 깨진다. 새 색이 필요하면
의미 토큰을 먼저 만들 것.

원시 토큰을 직접 쓰는 예외는 **관제 캔버스** 하나다. 라이트/다크와 무관하게
언제나 잉크색인 브랜드 표면이라 `canvas-*` 접두어로 따로 열어 두었다.

색은 `"R G B"` 세 숫자로 저장한다. Tailwind 가 `rgb(var(--x) / <alpha-value>)`
로 읽어야 `bg-surface-card/60` 같은 투명도 조합이 동작하기 때문이다.

## 3. 색

### 잉크 (브랜드 표면)

석유빛이 도는 흑연색. 순수 검정을 피한 이유는, 순검정 위에서는 어떤 색을
올려도 탁해지고 그림자가 지저분해지기 때문이다.

| 토큰 | HEX | 쓰임 |
|---|---|---|
| `ink-950` | `#070E12` | 눌린 상태 |
| `ink-900` | `#0B161B` | 레일 · 다크모드 페이지 |
| `ink-850` | `#0F1E25` | 관제 캔버스 · 다크모드 카드 |
| `ink-800` | `#14272F` | 다크모드 입력칸 |
| `ink-700` | `#1C3742` | 다크모드 헤어라인 · 격자선 |
| `ink-500` | `#3D6E7E` | 다이어그램 배경 운행선 |
| `ink-400` | `#68929F` | 잉크 위 보조 글자 |
| `ink-300` | `#9BB9C3` | 잉크 위 본문 |
| `ink-50` | `#F1F6F8` | 잉크 위 제목 |

### 종이 (업무 표면)

| 토큰 | HEX | 쓰임 |
|---|---|---|
| `paper-0` | `#FFFFFF` | 카드 · 입력칸 |
| `paper-50` | `#F6F8F9` | 페이지 바탕 |
| `paper-100` | `#EDF1F3` | 눌린 면 |
| `paper-200` | `#E0E7EA` | 헤어라인 |
| `paper-300` | `#C9D5DA` | 입력칸 테두리 |

### 옥색 — 유일한 유채색 강조

| 토큰 | HEX | 쓰임 |
|---|---|---|
| `jade-700` | `#066B60` | 라이트 배경의 링크 (6.4:1) |
| `jade-600` | `#08897B` | 포커스 링 (4.3:1) |
| `jade-400` | `#2FC4B0` | 다크 배경의 강조 · 진행 중인 운행 |
| `jade-300` | `#63D7C6` | 잉크 위 링크 |

**살아 있는 것에만 쓴다** — 포커스, 진행 중인 운행, 현재 시각. 버튼을 칠하는
데는 쓰지 않는다. 강조를 여기저기 뿌리면 그것은 강조가 아니라 배경이 된다.

### 주요 동작의 규칙

> 표면에서 가장 대비가 큰 색으로 칠한다.

라이트에서는 잉크(`--action-primary: ink-900`), 다크에서는 흰색(`paper-0`).
브랜드색이 아니라 대비가 주요 버튼을 만든다. 두 테마에서 규칙이 같으므로
"라이트는 검정 버튼, 다크는 옥색 버튼" 같은 어긋남이 생기지 않는다.

**한 화면에 primary 는 하나다.**

### 상태색

| 역할 | 라이트 | 다크 |
|---|---|---|
| 위험 · 오류 | `red-700` | `red-300` |
| 주의 · 지연 | `amber-700` | `amber-300` |
| 정상 · 완료 | `jade-700` | `jade-300` |

색만으로 뜻을 전하지 않는다. 상태에는 항상 아이콘이나 글자를 함께 둔다.
`Alert` 는 톤마다 다른 아이콘을 쓰고, 비밀번호 강도 표시는 눈금 옆에
`약함 / 보통 / 안전` 을 적는다.

### 대비 기준

본문 4.5:1, 큰 글자와 UI 요소 3:1 을 모든 조합에서 지킨다.
잉크 배경에서 `ink-500`·`ink-600` 은 본문 대비를 넘지 못한다 —
**작아서 덜 보여야 하는 글자는 색이 아니라 크기로 낮춘다.**

## 4. 타이포그래피

두 목소리로 쓴다.

| 서체 | 맡는 것 |
|---|---|
| **IBM Plex Sans KR** | 사람이 읽는 것 — 문장 · 라벨 · 제목 |
| **IBM Plex Mono** | 기계가 세는 것 — 오더번호 · 시각 · 수량 · 눈금 |

같은 집안이라 나란히 놓아도 어긋나지 않으면서 성격은 뚜렷이 갈린다.
하루 종일 표를 보는 화면에서 "이 값은 자릿수가 맞아야 하는 값" 이라는 신호를
서체가 대신 준다.

`next/font` 가 빌드 시점에 받아 같은 도메인에서 서빙한다. 사내망에서 외부
폰트 CDN 이 막혀 있어도 글자가 깨지지 않는다. 한글은 유니코드 구간이 100개
넘게 쪼개져 있어 preload 하지 않는다 — 브라우저가 실제로 쓰는 구간만 받는다.

### 크기 (8단계에서 끝낸다)

| 클래스 | px | 쓰임 |
|---|---|---|
| `text-display` | 40 | 브랜드 진술 |
| `text-display-sm` | 28 | 페이지 제목 |
| `text-title` | 22 | 화면 제목 |
| `text-title-sm` | 18 | 구획 제목 |
| `text-lead` | 16 | 안내 문장 · 큰 버튼 |
| `text-body` | 15 | 본문 (기본) |
| `text-label` | 13 | 입력 라벨 |
| `text-caption` | 12 | 도움말 · 오류 |

입력칸 글자는 모바일에서 16px 이다(`.field-text`). 그보다 작으면 iOS 가
화면을 확대해 버린다.

### 두 가지 마이크로 라벨

```
.eyebrow      라틴 · 숫자 전용. 고정폭 · 대문자 · 자간 0.16em
.eyebrow-ko   한글 전용. 12px · 자간 0.01em
```

`.eyebrow` 의 넓은 자간과 대문자 변환은 알파벳을 전제로 한 장치다. 한글에
그대로 걸면 `통 합 연 계` 처럼 낱글자가 흩어져 읽기가 나빠진다. **한글
마이크로 라벨에는 `.eyebrow` 를 쓰지 않는다.**

`.tabular` 는 고정폭 + `tabular-nums`. 숫자가 세로로 줄 맞아야 하는 모든 곳
(오더번호 · 시각 · 금액 · 코드)에 쓴다.

### tailwind-merge 주의

`cn()` 은 `text-body` 같은 자체 크기 토큰을 **font-size 그룹에 등록해 두어야**
한다(`src/lib/cn.ts`). 등록하지 않으면 tailwind-merge 가 이름만 보고 색으로
분류해서, 같은 요소의 진짜 색(`text-action-text`)을 중복이라며 지운다.
검은 버튼 위 흰 글자가 통째로 사라지는 식으로 드러난다.

`tailwind.config.ts` 의 `fontSize` 에 항목을 추가하면 `cn.ts` 에도 같이 넣을 것.

## 5. 여백 · 모서리 · 그림자

- **간격** : Tailwind 기본 4px 눈금. 필드 사이 20px(`space-y-5`), 구획 사이 32px
- **모서리** : `sm 4 / md 6 / lg 10 / card 14`. 버튼과 입력칸은 6px.
  알약 모양(9999)도, 각진 0 도 쓰지 않는다 — 정밀 계기의 모서리다.
- **그림자** : 잉크색을 섞는다. 순검정 그림자는 이 팔레트에서 탁해 보인다.

컨트롤 높이는 `sm 32 / md 40 / lg 48`. 누를 수 있는 것은 44px 이상을 확보한다
(아이콘이 18px 이어도 버튼은 44px).

## 6. 움직임

| 토큰 | 값 | 쓰임 |
|---|---|---|
| `--dur-fast` | 120ms | 색 · 테두리 변화 |
| `--dur-base` | 200ms | 상태 전환 |
| `--dur-slow` | 320ms | 등장 |
| `--ease-out` | `cubic-bezier(.22,.8,.28,1)` | 들어올 때 |
| `--ease-in` | `cubic-bezier(.5,0,.9,.6)` | 나갈 때 |

움직임은 **순서를 알려주는 안내**다. 장식이 아니다. 인증 화면의 등장 연출은
읽어야 하는 순서를 그대로 따라간다 — 눈금 → 제목 → 다이어그램 → 폼.

`prefers-reduced-motion` 을 켠 사용자에게는 duration 뿐 아니라 **delay 도
0 으로 만든다.** duration 만 지우면 2초 뒤에 툭 나타나는 동작이 그대로 남는다.

## 7. 폼

읽어야 할 것을 미리 주고, 틀린 곳은 그 자리에서 짚는다.

- 라벨은 항상 보인다. placeholder 로 대신하지 않는다.
- 도움말(`hint`)은 입력 **전에** 규칙을 알려주는 자리다.
- 오류는 해당 필드 바로 아래. 화면 맨 위에 모으면 긴 폼에서 다시 찾아 내려와야 한다.
- 검증은 blur 시점. 글자를 칠 때마다 빨개지지 않는다.
- 제출 실패 후 커서를 **고쳐야 할 첫 칸으로** 보낸다.
- 필수 표시 `*` 옆에는 `sr-only` 로 "필수" 를 적는다.

검증 규칙은 `@ntms/shared` 의 zod 스키마 한 벌을 API 와 화면이 공유한다.
화면은 통과시키는데 서버는 거절하는 상태가 생기지 않게 하려는 것이다.

## 8. 글쓰기

화면의 말은 장식이 아니라 재료다. 간격과 색을 정할 때와 같은 정도로 신경 쓴다.

- **사용자 쪽에서 쓴다.** 시스템이 어떻게 만들어졌는지가 아니라, 사람이 무엇을
  다루는지로 이름 붙인다. `테넌트 코드`가 아니라 `회사 코드`.
- **동작 이름은 흐름 내내 같다.** `계정 신청` 으로 시작했으면 버튼도
  `신청하기`, 완료 문구도 `신청이 접수되었습니다` 다.
- **오류는 원인과 다음에 할 일을 함께 적는다.** "입력이 올바르지 않습니다"
  대신 "비밀번호를 여러 번 틀려 계정이 잠겼습니다. 관리자에게 잠금 해제를
  요청해 주세요."
- **없는 기능을 있는 척하지 않는다.** 비밀번호 재설정 화면은 자동 발송 대신
  실제로 밟아야 하는 절차를 적는다.
- 서버는 **코드**를, 화면은 **문구**를 책임진다(`AUTH_ERROR_MESSAGE`).
  서버 메시지를 그대로 흘리면 문구를 고칠 때마다 서버를 배포해야 한다.

## 9. 접근성 기준선

- 대비 : 본문 4.5:1, UI 요소 3:1
- 포커스 : `:focus-visible` 에 2px 옥색 링 + 2px 표면색 간격.
  **모서리 반경은 건드리지 않는다** — 포커스가 갈 때마다 모양이 바뀐다.
- 제목 : 화면마다 `h1` 하나. 1024px 아래에서 감춰지는 영역에는 `h1` 을 두지 않는다.
- 오류 : `role="alert"`, 심각한 것은 `aria-live="assertive"`, 나머지는 `polite`
- 아이콘 전용 버튼에는 `aria-label`. 비밀번호 보기 토글은 탭 순서에 남긴다 —
  키보드만 쓰는 사용자에게서 확인 수단을 빼앗지 않는다.
- 확대를 막지 않는다(`maximum-scale` 을 쓰지 않는다).
- 차트에는 범례를 붙인다. 범례 없는 그림은 그림에 그친다.

## 10. 화면 골격

```
┌──┬─────────────────────────────┬──────────────┐
│레│                             │              │
│일│      관제 캔버스 (잉크)      │  폼 (종이)   │
│76│      · 브랜드 진술           │  · 제목      │
│px│      · 운행 다이어그램       │  · 입력      │
│  │      · 범례                  │  · 주요 동작 │
└──┴─────────────────────────────┴──────────────┘
                                      33rem
```

레일은 제품의 척추다. 로그인 이후 앱 셸에서 접힌 내비게이션 레일이 같은
자리에 그대로 남는다. 처음 보는 화면과 매일 보는 화면이 같은 뼈대를 쓴다.

**1024px 아래** : 캔버스를 접고 레일을 상단 바로 눕힌다. 폼은 어느 폭에서도
한 단으로 유지된다.

## 10-1. 앱 셸

로그인 이후의 골격. 레일은 인증 화면의 그것과 **같은 자리 · 같은 폭(76px)** 이다.
처음 보는 화면과 매일 보는 화면이 같은 뼈대를 쓴다.

```
┌────┬─────────────┬────────────────────────────────┐
│레일│ 메뉴 패널    │ 상단바 (56px)                   │
│76px│ 232px       ├────────────────────────────────┤
│    │             │                                │
│모듈│ 하위 화면    │ 본문                           │
│8개 │             │                                │
└────┴─────────────┴────────────────────────────────┘
```

두 단으로 나눈 것은 데이터 구조를 그대로 따른 것이다 — `ntms.menu` 의 계층이
두 단계라 내비게이션도 두 단이면 충분하다.

| 영역 | 담는 것 | 표면 |
|---|---|---|
| 레일 | 최상위 메뉴(모듈). 아이콘 + 한글 라벨 | `canvas-900` |
| 패널 | 그 모듈의 하위 화면 | `canvas-850` |
| 상단바 | 현재 위치(빵부스러기) · 계정 메뉴 | `surface-card` |
| 본문 | 화면 | `surface-page` |

### 규칙

- **아이콘만 두지 않는다.** 레일 항목은 11px 한글 라벨을 함께 단다.
  아이콘만으로는 무엇인지 배우는 데 시간이 걸리고, 그 시간은 매일 반복된다.
- **하위 화면이 없는 모듈에는 패널을 띄우지 않는다.** 제목과 항목이 같은 이름으로
  두 번 나오면 고장난 것처럼 보인다. 본문이 그만큼 넓어진다.
- **패널 접기 상태는 기억한다**(`localStorage`). 넓게 쓰던 사람이 새로고침마다
  다시 접어야 하면 안 된다.
- **경로가 없는 메뉴는 링크로 만들지 않는다.** 그룹일 뿐이라 갈 곳이 없다.
- **1024px 아래**에서는 레일과 패널을 하나의 서랍으로 합친다. 화면을 옮기면 닫는다.

### 메뉴는 데이터에서 온다

내비게이션을 코드에 박지 않는다. `GET /auth/menus` 가 그 사람의 역할로 걸러
내려주므로, 권한을 바꾸면 배포 없이 화면 구성이 바뀐다.

**메뉴를 감추는 것은 안내이지 차단이 아니다.** 실제 차단은 언제나 서버의
권한 검사가 한다.

아직 만들지 않은 화면은 `(app)/[...slug]` 가 받아 "준비 중" 이라고 분명히
말한다. 메뉴는 DB 에서 오므로 화면보다 먼저 생기는데, 그 사이를 404 로 두면
내비게이션이 죽은 링크투성이가 되고, 그럴듯한 빈 화면을 두면 고장을 의심하게
된다. 실제 화면이 생기면 그 라우트가 자동으로 우선한다.

## 10-2. 자격증명 화면

비밀번호 변경은 **업무 셸이 아니라 인증 셸**에 둔다. 강제로 넘어온 사람은 아직
앱 안으로 들어온 것이 아니고, 자발적으로 온 사람에게도 한 가지 일에만 집중하는
화면이 낫다.

강제(초기 비밀번호 · 만료)와 자발(계정 메뉴) 두 경로가 **같은 화면**을 쓴다.
할 일이 같기 때문이다. 안내 문구만 갈린다 — 화면을 둘로 나누면 규칙도 갈라진다.

바꾸고 나면 **다른 기기만** 로그아웃되고 지금 창은 유지된다. 바꾼 사람까지
내보내면 "바꿨더니 로그아웃됐다" 가 되어, 정작 급할 때 바꾸기를 꺼리게 된다.

## 10-3. 업무 프로세스와 화면

TMS 의 하루는 한 줄로 흐른다. 메뉴 구조도, 상태 색도, 메인화면도 전부
이 한 줄에서 나온다.

```
[ 운송계획 ]                                    [ 실행 ]   [ 정산 ]
오더 접수 → 편성(상차조합) → 운송사 배정 → 배차 → 운송실행 → 실적 → 정산
```

`ntms.menu` 의 최상위 7개(관제 현황 · 운송계획 · 운송실행 · 실적 · 정산 ·
기준정보 · 시스템관리)가 이 흐름을 그대로 따른다. 화면을 새로 만들 때는
"이 화면이 위 줄의 어디에 있는가" 를 먼저 정한다.

### 메인화면의 얼굴 — 운송 파이프라인

관제 현황의 주인공은 큰 숫자 카드가 아니라 **파이프라인 다이어그램**이다.

> **축 위로 흐르고, 축 아래로 쌓인다.**
>
> · 마디를 잇는 선의 두께 = 그 단계로 넘어간 오더 수 (흐름)
> · 축 아래로 내려간 막대 = 그 단계에 머무는 오더 수 (정체)

선이 가늘어지는 곳에서 일이 멈추고, 막대가 길어지는 곳에 일이 고인다.
두 신호가 만나는 자리가 오늘의 병목이다. 배차 담당자가 아침에 알아야 하는
것은 "몇 건 처리했나" 가 아니라 "지금 어디에 얼마나 쌓여 있나" 이기 때문이다.

로그인 화면의 운행 다이어그램과 **같은 언어(축 · 마디 · 눈금)** 를 쓴다.
처음 본 그림이 앱 안에서 계속 이어진다.

막대 색은 세 가지뿐이다.

| 색 | 뜻 |
|---|---|
| `canvas-500` | 그냥 쌓여 있다 |
| `amber-300` | 손대야 할 정체 (임계 초과) |
| `jade-400` | 도로 위 — 정체가 아니라 진행 |

운송 단계에 머무는 것을 병목으로 칠하지 않는다. 그러면 매일 빨간 화면을
보게 되고, 빨강이 뜻을 잃는다.

### 상태는 국면으로 접는다

오더 상태만 15가지다. 상태마다 색을 하나씩 주면 색이 아무 뜻도 전하지 못한다.
**국면(phase) 네 가지**로 접어서 말한다(`ORDER_STATUS_PHASE`).

| 국면 | 뜻 | 톤 |
|---|---|---|
| `planned` | 아직 움직이지 않았다 | 중립 |
| `active` | 지금 움직이고 있다 | 옥색 — 이 시스템에서 옥색은 살아 있는 것 |
| `done` | 끝났다 | 조용한 성공 |
| `problem` | 손을 대야 한다 | 호박 · 적색 |

`StatusChip` 은 국면마다 앞머리 표식의 모양도 다르게 한다. 색만으로 말하지
않기 위해서다.

## 10-4. 목록 화면의 뼈대

TMS 화면의 대부분은 표다. 오더 · 트립 · 배차 · 차량 · 정산 명세가 모두 같은
모양이어야 사람이 화면마다 다시 배우지 않는다. 그래서 표는 화면마다 만들지
않고 `components/tms/data-table.tsx` 하나만 둔다.

```
조건 줄  →  조건에 걸린 합계  →  표  →  쪽 넘김
```

합계를 표 **위**에 두는 이유는, 조건을 바꿀 때마다 "몇 건 · 몇 톤" 이 먼저
눈에 들어와야 하기 때문이다. 아래에 두면 스크롤해야 보인다. 그리고 합계는
**페이지가 아니라 조건 전체**를 더한 값이어야 한다 — 20건짜리 페이지의
합계는 아무도 궁금해하지 않는다.

### 표 규칙

- 숫자는 오른쪽 정렬 + `.tabular`. 자릿수가 세로로 맞아야 눈으로 비교된다.
- 머리글은 스크롤에 붙어 있는다(`sticky`). 200줄을 내려가도 무슨 열인지 알아야 한다.
- **줄무늬(zebra)를 쓰지 않는다.** 헤어라인으로 충분하고, 줄무늬는 상태 색과 싸운다.
- 행 전체가 눌린다. 좁은 링크 하나를 조준하게 하지 않는다.
- 정렬 가능한 열은 `aria-sort` 를 단다.
- 정렬 키는 서버에서 **허용 목록으로 검증**한다. 쿼리 문자열을 그대로
  `orderBy` 에 넘기지 않는다.

### 거르개

자주 쓰는 상태 몇 개만 버튼으로 꺼내 두고 나머지는 목록에 남긴다.
15개를 드롭다운에 다 넣으면 고를 수가 없다.
