# 0001. 화면 단위 REST 창구로 간다 — GraphQL 을 쓰지 않는다

> 최종 수정: 2026-09-06

- 상태: 채택
- 결정일: 2026-08-18 (첫 컨트롤러가 들어온 날 `69b5c22`. 이후 문서를 고쳐도
  이 값은 바꾸지 않는다)
- 관련: [`06-api/README.md`](../06-api/README.md) · [인수인계 문서](../handoff.md) 3절

## 배경

TMS 화면은 **화면마다 필요한 모양이 다르다.** 관제 현황은 파이프라인 마디별
집계 하나면 끝나고(`GET /dashboard/overview` 한 창구가 화면 전체를 채운다),
정산 상세는 명세·부대비·조정·산출근거·관문을 한 번에 봐야 하며, 기준정보는
여덟 개 표의 평범한 CRUD 다. 같은 데이터를 화면마다 다르게 접어서 봐야 한다.

지금 규모(2026-09-06 실측. 결정은 이보다 훨씬 작을 때 내렸고, 그 뒤로도
뒤집을 이유가 없었다):

| | 수 |
|---|---|
| 창구 | 130개 · 컨트롤러 12개 |
| 화면 | 39개 |
| `packages/shared` 의 zod 스키마 | 49개 |
| `@ntms/shared` 를 import 하는 파일 | web 75 · api 35 |

마지막 두 줄이 이 결정의 전제다. **클라이언트와 서버가 이미 같은 타입을**
**컴파일 시점에 공유한다.** 모노레포이고 양쪽 다 TypeScript 이며, 요청 스키마는
zod 로 한 곳에 정의해 컨트롤러가 `parse` 하고 화면이 같은 것으로 폼을 만든다.

## 선택지

1. **화면 단위 REST 창구** — 창구 하나가 한 화면(또는 한 동작)에 답한다.
   - 장점: 화면이 무엇을 받는지 창구 하나만 보면 안다. 접기·집계를 서버가
     정하므로 판정 로직을 `packages/shared` 로 몰아 둔 구조와 결이 같다.
     캐시·권한·감사가 창구 단위로 붙어 추적이 쉽다.
   - 단점: 화면이 늘면 창구도 는다. 비슷한 창구가 여럿 생긴다.
     한 화면이 여러 창구를 부르는 경우가 생긴다.

2. **GraphQL 단일 창구** — 화면이 필요한 모양을 스스로 조립한다.
   - 장점: 화면이 늘어도 창구가 안 는다. 과다·과소 조회가 준다.
   - 단점: 이 저장소가 GraphQL 로 얻을 가장 큰 것(타입 공유)을 **이미 zod 와
     모노레포로 얻고 있다.** 대신 N+1 방지(dataloader), 질의 깊이·복잡도 제한,
     필드 단위 권한, RLS 컨텍스트를 리졸버마다 태우는 일이 새로 생긴다.
     RLS 를 `prisma.run()` 한 겹으로 강제하는 지금 구조와 특히 안 맞는다 —
     리졸버가 여러 갈래로 DB 를 부르면 그 겹을 빠뜨린 자리가 **오류가 아니라**
     **0행**으로 조용히 나온다(인수인계 4절).

## 결정

**1안.** 결정적인 이유 하나는 **GraphQL 이 주는 핵심 이득을 이미 가지고 있다**는
것이다. 클라이언트-서버 타입 계약은 zod 스키마 49개가 담당하고 있고, 그것을
얻으려고 리졸버·로더·복잡도 제한·필드 권한이라는 새 표면을 여는 것은
이 규모(화면 39개 · 개발 인원 소수)에서 남는 장사가 아니다.

## 트레이드오프

- **포기한 것:** 화면이 필요한 모양을 스스로 조립하는 능력. 새 화면을 만들 때마다
  창구를 하나 더 판다. 창구 130개는 이미 사람이 한눈에 못 외우는 수라,
  「창구 목록은 컨트롤러가 원본」이라는 규칙에 기대고 있다.
- **감수한 위험:** 비슷한 창구가 늘어 같은 집계가 두 군데에서 따로 계산될 수
  있다. 지금은 판정·집계를 `packages/shared` 에 두어 막고 있지만, 이 규칙이
  느슨해지면 바로 드러나는 위험이다.
- **재검토 조건:** 아래 중 **하나라도** 걸리면 이 결정을 다시 본다.
  - 창구가 **200개**를 넘는다 (결정 시점 130. 화면당 평균 3.3개가 유지된다면
    화면 60개 언저리다)
  - 한 화면이 첫 그림을 그리는 데 **읽기 창구 8개 이상**을 부른다
    (지금 최대는 사용자·권한과 감사로그의 `useApiQuery` 4개다. 정산 상세는
    호출이 12개로 가장 많지만 그중 10개가 쓰기라 이 조건과 무관하다)
  - **외부(운송사 포털·화주 포털)에 창구를 연다.** 우리가 화면을 안 만드는
    소비자가 생기면 "화면 단위" 라는 전제 자체가 깨진다
  - 모바일 등 **대역폭이 제약인 클라이언트**가 생겨 과다 조회가 실측으로 문제가 된다
